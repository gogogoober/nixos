# Hugo's NixOS Config

One flake, several machines. Everything in this repo is the declarative
configuration for those machines, and essentially every task here is about
optimizing or improving that configuration. There is no application code to
ship.

## Start by identifying the host

Run `hostname`, then read `docs/hosts/<hostname>.md` before changing anything.
That file carries the machine's goal, its hardware limits, the failures already
diagnosed on it, and the dead ends not worth reopening. Each host has a
different goal, so the same change is not equally right everywhere.

| Host | Session | Goal |
| --- | --- | --- |
| `surface-go-3` | GNOME | Battery life on a fanless 8 GB tablet, then touch-only usability |
| `dell-old` | Hyprland | Development host for the custom desktop stack |

## Architecture

### Layers

```
flake.nix              inputs, nixosConfigurations, flake-parts perSystem
hosts/<name>/          identity + which modules that machine turns on
  default.nix            hand-written switchboard
  hardware.nix           generated by nixos-generate-config, do not edit
modules/nixos/         system modules, one concern each
modules/home-manager/  user modules, same pattern
home/hugo/             the home-manager profile, wired in by modules/nixos/user.nix
overlays/              pkgs.unstable escape hatch
packages/              per-system packages, currently empty
assets/                wallpapers, nvim config, claude seed tree
docs/                  this documentation, including docs/hosts/
utils/scripts/         one-off helper scripts, not part of the system
.ai/                   PRDs and reference configs, tracked in git
```

### Flake and flake-parts

`flake-parts` owns the `perSystem` half: the dev shell, `nix fmt` via
`nixfmt-tree`, and `packages`. The `nixosConfigurations` are declared in the
plain `flake` block, one `nixpkgs.lib.nixosSystem` per host, each importing its
host directory plus the home-manager NixOS module with
`extraSpecialArgs = { inherit inputs; }`.

nixpkgs is pinned to the stable release. `nixpkgs-unstable` is a second input
exposed through `overlays/default.nix` as `pkgs.unstable.<name>`, for the few
packages that must outpace stable. Reach for it sparingly.

### The module contract

Every module follows the same shape, and new ones should too:

```nix
let
  inherit (lib) mkEnableOption mkIf;
  cfg = config.modules.thing;
in
{
  options.modules.thing.enable = mkEnableOption "what it does";
  config = mkIf cfg.enable { ... };
}
```

Everything lives under the `modules.*` option namespace, so a host file reads
as a list of switches and nothing else. `common`, `power`, and `firefox` default
to true and are usually not listed; everything else is opt-in per host.

Four conventions hold across the tree:

**Modules claim their own groups.** A module that needs a user in a group adds
it, rather than `user.nix` carrying a hardcoded list. `developer.nix` adds
`docker`, `tts.nix` adds `ydotool`, `common.nix` adds `networkmanager`.

**System modules flip their home-manager counterpart.** `modules/nixos/gnome.nix`
sets `home-manager.users.<name>.modules.gnome.enable = true`, and hyprland does
the same, so a host enables a desktop with one switch instead of two.

**Dependencies are assertions, not comments.** `gnome` and `hyprland` both
assert that `desktop` is enabled, because the display manager and pipewire live
there.

**Tunables are hoisted.** Anything a reader might want to change goes in a
named `settings` attrset or a `let` binding at the top of the file, never
threaded as a literal through the body. See `tts.nix`, `stt.nix`, and
`charger-watch.nix` for the pattern.

### Where user config lives

`modules/nixos/user.nix` defines `modules.user` with the name, description,
groups, and a path to the home-manager config, then wires
`home-manager.users.<name>` to it. Nothing else in the tree hardcodes a
username; use `config.modules.user.name`.

`modules/home-manager/design-system/` holds colour, font, and structure tokens
sourced from `docs/design-system/`. The Hyprland modules import them directly
rather than through the module system.

## Workflow

Use the Justfile, not raw `nixos-rebuild`:

- `just rebuild "<message>"` — formats, stages, builds, and only commits if the
  build succeeded, with the new generation number prefixed to the message
- `just test` — `nix flake check`
- `just format` — `nix fmt`
- `just log` — tail the last rebuild
- `just clean` — prune generations, caches, and the journal
- `just update` — update every flake input, rebuild, then clean

`just extra=<flag> rebuild "..."` passes extra flags through to `nixos-rebuild`.

Before touching the real config on anything non-trivial: read the references,
write a PRD in `.ai/prds/`, agree on it, then apply. The existing PRDs are the
record of what was tried and why, and are worth reading before re-solving
something.

## Repo-wide gotchas

Host-specific failures live in the host files. This section is only for things
that bite on any machine.

### Bootloader refuses to downgrade after a channel move

Moving to an older nixpkgs builds fine and then dies on the last step with
`Failed to install bootloader`. The ESP holds a newer systemd-boot than the
release ships, and `bootctl update` will not go backwards, so it skips both
`.efi` files and exits non-zero. Nothing has activated at that point, and the
half-built generation has no boot entry.

Rerun forcing `bootctl install`:

```
just extra=--install-bootloader rebuild "<message>"
```

If every later rebuild fails the same way, with `updating systemd-boot from
260.1 to 260.2` followed by `same boot loader version in place already`, the
cause is a stale `EFI/systemd/systemd-boot-fallbackx64.efi`. systemd 261's
`bootctl` writes that fallback copy and older releases never touch it; the
NixOS installer takes the first version `bootctl status` lists, which is the
fallback, so it requests an update that has nothing to do. Delete it once:

```
sudo rm /boot/EFI/systemd/systemd-boot-fallbackx64.efi
```
